# 🤝 Contributing

Obrigado pelo interesse em contribuir com o DDOS (Dekassegui Digital Operating System).

Este projeto é mais do que código: é um conjunto de padrões, documentação e processos criados para preservar conhecimento e manter consistência entre desenvolvedores humanos e Inteligências Artificiais.

---

# Antes de contribuir

Todo colaborador deve conhecer:

- 📖 COMPANY_PHILOSOPHY
- 🧭 SOURCE_OF_TRUTH
- 🤖 AI_ONBOARDING
- 🛠 DEVELOPMENT_STANDARD
- 🐕 KAIZEN
- 🗺 ROADMAP

Nenhuma implementação deve começar sem compreender esses documentos.

---

# Filosofia

O DDOS segue alguns princípios inegociáveis.

- Documentar antes de esquecer.
- Simplicidade antes da complexidade.
- Performance como requisito.
- Segurança por padrão.
- Código limpo.
- WordPress deve permanecer editável.
- IA auxilia pessoas, não substitui entendimento.

---

# Padrões de contribuição

Toda contribuição deve:

✅ seguir os padrões do DDOS

✅ manter a documentação atualizada

✅ evitar duplicação

✅ preservar compatibilidade

✅ priorizar manutenção humana

---

# O que evitar

Não aceitamos mudanças que:

- compliquem desnecessariamente a arquitetura;
- adicionem CSS quando o recurso nativo resolve;
- escondam lógica sem documentação;
- quebrem a editabilidade do Elementor;
- introduzam dependências sem necessidade.

---

# Fluxo recomendado

1. Ler a documentação.
2. Compreender o problema.
3. Planejar.
4. Implementar.
5. Validar.
6. Documentar.
7. Versionar.

Nunca pule etapas.

---

# Inteligências Artificiais

Antes de gerar qualquer código, uma IA deve:

- compreender a filosofia;
- carregar os padrões;
- respeitar o Source of Truth;
- identificar o tipo do projeto;
- produzir soluções compatíveis com o DDOS.

---

# Objetivo

Criar um ecossistema onde qualquer desenvolvedor — humano ou IA — consiga continuar um projeto sem depender de quem o iniciou.

---

# Regra de Ouro

Todo projeto desenvolvido seguindo o DDOS deve permanecer editável por outro desenvolvedor utilizando preferencialmente os recursos nativos da plataforma.

Nenhuma solução técnica deve dificultar a manutenção humana apenas por ser mais rápida de implementar.

Se um recurso puder ser resolvido pelo Elementor, WordPress ou pela plataforma utilizada, essa será sempre a primeira escolha.

CSS, JavaScript ou código personalizado somente quando forem realmente necessários e devidamente documentados.
